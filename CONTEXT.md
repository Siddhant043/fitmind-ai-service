# ai-service — Domain Glossary

## Query Evaluator

The single classification step that runs on every incoming chat message, before any retrieval or
generation happens. Replaces the prior "intent classification" step: same job (deciding which
graph branch handles the message), extended with three additional judgments about how to handle
it. Produces a structured result with four fields: **Intent**, **Needs User Data**,
**Query Complexity**, and **Multi-Hop**.

Runs on the fast model tier — the schema is small and well-defined enough that the cheaper model
is sufficient, and this call is on the hot path for every message.

## Intent

The existing nine-way classification of a chat message's purpose: `fitness_rag`, `nutrition_rag`,
`workout_plan_create`, `workout_day_create`, `workout_history`, `meal_history`, `progress_review`,
`challenge_suggest`, `general` — plus `safety`, which is short-circuited by a keyword regex before
the Query Evaluator ever runs (unchanged by this work). Drives which graph branch a message takes
(RAG retrieval, direct generation, tool-calling agent, etc.).

## Needs User Data

A boolean judgment from the Query Evaluator: does answering this message require the user's
detailed logged data (last meal, last workout, recent meals) rather than just their static profile
(height/weight/goal/TDEE, which is always present in every prompt regardless of this flag)?

Governs two things for the `workout_history` / `meal_history` / `progress_review` intents: (1)
whether the detailed data sections are included in the prompt, and (2) whether the message is
routed straight to a direct-answer generation step instead of through the tool-calling agent. For
all other intents, this flag has no effect on routing.

## Query Complexity

A `fast` | `deep` judgment from the Query Evaluator: should the final response be generated by the
fast model tier or the deep (chat) model tier? Only applies to pure text-generation steps — the
tool-calling agent path always uses the deep tier regardless of this signal, since tool
selection/argument construction benefits more from the stronger model.

## Multi-Hop Query

A boolean judgment from the Query Evaluator, meaningful only for `fitness_rag` / `nutrition_rag`
intents: does answering this knowledge-base question require retrieving passages for more than one
distinct sub-question, rather than one retrieval pass over the question as a whole? Bounded to at
most 3 sub-questions. Each sub-question is retrieved independently and the results are merged and
capped before being placed in the prompt.

Scoped deliberately to *single-domain* decomposition (splitting one fitness/nutrition question into
retrieval sub-questions). Cross-domain queries that span multiple intents at once (e.g. combining
the user's own meal history with workout history and general nutrition knowledge in one answer) are
a distinct, larger capability — handling that well likely means giving the tool-calling agent RAG
retrieval as a tool it can call repeatedly, rather than extending Multi-Hop Query. Not built in this
pass.
